## 签名

协议文件 `signature` 段是准确定义，含两组测试向量，固件实现后先用测试向量自检。嵌入式已按此实现（`swap_registry.lua` 的 `verify`/`hmac`）。

- **算法**：HMAC-SHA256，输出小写十六进制 64 字符。每台柜一把 32 字节密钥，用 `key_id` 标识（当前 `k1`）；密钥不经蓝牙传输、不写日志。
- **签名原文**：字段按固定顺序转文本，用 `|` 连接（整数十进制、布尔 1/0、null 为空串），不对 JSON 文本签名。
  - 指令：`H-SWAP-v1|device_id|challenge|order_id|return_slot|return_bt_code|release_slot|release_bt_code|lock_if_overdue|min_release_soc`
  - 结果：`H-RESULT-v1|device_id|order_id|result|state_seq|return_slot|release_slot|return_bt_code_read|release_bt_code_read`
- **challenge**：每次收到 connect 用硬件随机源生成 16 字节，在 device_info 中下发；断开即作废。所以录下来的旧指令无法重放，也不需要柜端时钟或 TCP。
- **密钥写入**：柜机从 `fskv` 的 `SwapJSONKeys = { current = 'k1', keys = { k1 = 32 字节原始密钥 } }` 读取。每台柜机的密钥由平台按柜号算出（服务器上 `scripts/ble-cabinet-key.mjs <柜号>`），写入方式由嵌入式提供（串口/配置工具/生产工装），这是目前唯一待定的环节。
- **测试密钥**：`signature.test_vectors` 里的密钥只用于自检，严禁写入真实柜机。

## 120 秒连接上限（修订 4）

- 单次连接从建立起最长 120 秒：手机在确认 swap_result 后立即断开；满 120 秒时固件也应主动断开。
- 断开不取消订单：柜机继续按状态机执行并持久保存结果。骑手重新扫码连接后，手机先 swap_query，柜机补报未确认的终态。

## 嵌入式实现顺序

1. **先建 BLE 收发链路。** EA01 通知先启用，然后手机向 EA02 发 connect。默认一次写不超过 20 字节；已协商 MTU 时按 `min(MTU-3, 平台单次写上限)` 分片。每方向按完整 JSON 行串行发送，不能交错两条消息。每片收到 GATT 写完成回调再继续；设备端通知受发送完成/可发送状态控制。write 回调成功只代表链路接收，不是业务 ack。
2. **按行组包。** 接收字节先缓冲，LF 到达后再 UTF-8 解码和 JSON parse。中文字符可能跨分片，不能每片单独解码。超长行丢到下一个 LF；断线丢未完成行和连接队列，但不能丢柜端订单记录。Lua JSON `null` 应使用库的 null 哨兵，不能用 `nil` 让必填键消失；Lua `false` 也不能被 `value or default` 改写。
3. **先完成版本和身份握手。** connect 校验设备号与 `protocol_version=2.1.0`，不匹配按 ack code 回答且不开换电。成功后返回 device_info；主机收到后请求全量快照。新旧十六进制和 JSON 固件必须按明确版本升级，不要同一特征上猜测格式或静默回退。
4. **实现原子快照。** 在柜端采集模型上复制同一份快照，再发送 status、每仓 slot_status/battery_status、snapshot_end。每条带相同 boot_id/report_seq/snapshot_id。主机暂存并校验每仓恰好一组；有缺项、冲突或总计 30 秒/连续 3 秒无进展就整批丢弃并重取。重要 ack 和订单消息在消息边界优先于遥测，但不要切断当前 JSON 行。
5. **验证真实字段来源。** battery_present 的 0 必须由真实在位传感器/明确取出事件支持；缺 BT、485 断开、电压零单独不能填空仓。未知填 null。disabled/abnormal 未初始化也填 null，不能默认正常。电池 current 是充电电流，只允许非负数或 null；`0` 必须是实测零，不能用作缺数据占位。SOC 只发真实测量值。
6. **做持久订单状态机。** 接收 swap 后先验证参数与仓况，在 TCP/BLE 共享的临界区以 device_id+order_id 去重，持久化参数和 accepted 状态，再排入唯一执行队列并 ack。每个会产生物理副作用的阶段先保存阶段，再驱动门锁；要用门反馈、BT/485/SOC 与取出检测确认状态，不能用“写了开门 GPIO”代表门已开或电池已拿走。重启时先恢复活动订单；无法确认实物状态进入 recovery_required，不自动重做动作。
7. **支持查询和幂等恢复。** TCP 转 BLE 使用同一 order_id、仓号、BT 码、逾期策略及最低 SOC。ack 超时先查询；只有查询到 not_found 且服务端仍授权时，才可用原订单号和原参数再次提交。已受理的订单重发只回原进度/终态，不二次开门；终态先持久化再上报，断线后重报原订单结果。不同订单在柜忙时拒绝新订单，不得把失败写到旧订单。
8. **按实际动作产出结果。** 门没确认打开、还电 BT 不匹配、电量不足、释放电池仍在仓等结果必须由实际传感器和状态机判定。result 26/27 仍对应原 485/电压比对方式，但只有回收验证完成、出仓门已确认打开且电池已确认取走才可标 completed。无法确认电池去向时报告 recovery_required，不猜成功/失败。

## 当前需要硬件方确认

- `status.signal` 的 0..5 原始来源和映射。修订稿保留范围，没有替固件猜信号强弱方向。
- `battery_present` 是否有真实传感器，旧 `Box_Exist`/采集字段是否存在、各返回值含义。
- 门状态、仓内电压、BT、485、SOC 的采样更新时机，以及电池“已取走”如何由现有硬件可靠确认。
- 保留原固件各机械动作的已验证超时值。3 秒是通信 ack/订单 fallback 时间，不是开门或放电池时间。
- 密钥写入 fskv 的方式（串口、配置工具或生产工装）。
- 单次连接满 120 秒主动断开，且不影响执行中的订单与结果保存。
- 用设备日志验证协议版本、GATT UUID、write/notify、20 字节分片、中文 LF 分帧、整柜快照，以及断开/重启时活动订单恢复。

其中前三项与传感器/采样相关，协议本身无法制造缺失的硬件事实。若旧 Lua 只有状态读取、原十六进制 swap 解析或不持久订单表，需要实现对应 JSON 解析器、快照与订单模块后再上柜；仅换服务端/小程序协议文件不能让现有固件执行 JSON 换电。

## 修订 5（2026-11-03 现场联调后）

- 手机不再 ack 遥测（status、slot_status、battery_status、board_version，含快照中的这些行）。固件本就不等待、不重发遥测 ack，无需改动。仍需 ack 的：device_info、snapshot_end、swap_state、swap_result（手机 ack 柜机），以及 connect、snapshot_get、swap、swap_query（柜机 ack 手机）。
- 整数请按整数文本编码。现场柜机输出 `"id":1.000000000000000`、`"code":0.00000000000000e-308`、`"snapshot_id":1.20874406400000e+09`，是 LuatOS `%g` 的问题，行长约翻倍。`lua/ble_json_codec.lua` 已改为整数用 `%d`、小数最多 3 位并去掉末尾 0。
- 签名原文中的数字改为 `string.format('%d', …)`（`swap_registry.lua` 的 `verify`、`ble_json_protocol.lua` 的结果签名），避免 `tostring` 在该固件上输出非整数文本导致签名不一致。
- 建议：连接期间遥测只在变化时发送且合并（当前约每 3 秒整柜重发）；完整快照发送期间暂停变化推送。
- 现场日志仍显示全部仓 `battery_present=null`，请确认 `Box_Exist` 的真实采集来源；否则平台视所有仓为未知、不可选。

## 修订 6（2026-11-04 14:27 现场日志后）

- **现象**：柜机 14:27:42 把 `snapshot_end`（id 25）交给协议栈，3 次发送均未获 ack；手机 ack 在 14:28:46 才到，被判为“迟到ack”，此时手机已提示“未收到完整仓位信息”。
- **原因**：`write_notify` 返回成功只代表交给协议栈排队，不代表已发到手机。约 6.5 KB 快照用了约 65 秒才送达，下行约 90 字节/秒；手机带应答写入约 0.3 秒一次，推断连接间隔约 150–250 毫秒。一条约 280 字节的仓位行要约 3 秒才到，超过了手机 3 秒无进展时限。
- **最需要嵌入式确认**：连接建立后实际使用的连接间隔、从机延迟和监督超时，并在 LuatOS 有接口时请求 15–30 毫秒、延迟 0、超时 4–6 秒。新 `ble_server.lua` 会在连接事件里打印协议栈给出的全部参数（“连接事件参数”），请据此确认。
- **`lua/` 已做的修改（未编译，请编译后实测）**：
  - `ble_server(1).lua`：通知分片跟随本连接收到的最长单次 EA02 写入（上限 180 字节；日志“通知分片调整为”）；大分片 3 秒未被接受时本连接改回 20 字节（日志“大分片通知3秒未被接受”）。按 10 毫秒/字节估算协议栈积压，在发送完成回调里把估计值交给协议层。连接参数缩短后请重新测速并调小 `AIR_MS_PER_BYTE`。
  - `ble_json_protocol(1).lua`：关键消息的 3 秒 ack 计时从估计实际发出后起算（日志“关键消息已交协议栈，预计空口还需ms”）；`snapshot_end` 获 ack 或 3 次发送均超时前，暂停变化遥测，`board_version` 也延后到那时发送。
  - 修改前的文件在 `lua/backup-20261104-airtime/`。
- **手机端同步修改**：快照进展按收到的任何通知字节计，无进展 5 秒、总时限 60 秒。即使连接间隔不改，新固件加新小程序也能在约 60 秒内收齐快照；要做到几秒内完成，必须缩短连接间隔。

## 2026-11-11 修订 7：全网共用一把签名密钥（取代上文“每台柜机一把”与 `SwapJSONKeys`）

现场 2026-11-10 17:52：柜机用 k1 验签已通过，但 `SwapJSONKeys` 缺 `current`，签结果前检查失败回 ack 5。用户决定改为全网一把密钥，固件只存一个值：

- 存储：`fskv` 的 `SwapKey` = 32 字节原始密钥。验 `swap` 和签 `swap_result` 都用它；`key_id` 固定 `k1`，柜端不按 key_id 选密钥，结果里原样回填 `k1`。
- 未写密钥：`swap` 回 ack 9（`network key not provisioned`）；不会再出现“验签通过却回 5”。
- 密钥来源：平台运维在服务器上执行（输出是机密，只交刷写人员，不进聊天/群/工单/日志）：
  `cd /opt/aihuandian/current && sudo /usr/bin/node --env-file=/etc/aihuandian/platform.env scripts/ble-network-key.mjs`
  输出 `{"keyId":"k1","keyHex":"<64位十六进制>"}`，所有柜机写同一个 keyHex。
- 已修改（未编译，备份 `lua/backup-20261111-netkey/`）：`swap_registry(1).lua` 的 `M.key()`、`M.provision_key(hex)`、`M.hmac(input)`、`M.KEY_ID='k1'`；`ble_json_protocol(1).lua` 去掉 current 检查，结果签名改用 `orders.hmac(input)`。
- 写入入口示例（只挂本地调试串口，不能挂蓝牙，不要打印收到的行）：

```lua
local registry = require 'swap_registry'
local UART_ID, BAUD = 1, 115200
local buf = ''
uart.setup(UART_ID, BAUD, 8, 1)
local function reply(text) uart.write(UART_ID, text .. '\r\n') end
local function handle(line)
    local hex = line:match('^SWAPKEY%s+(%x+)$')
    if hex then
        local ok, err = registry.provision_key(hex); hex = nil
        reply(ok and 'SWAPKEY OK' or ('SWAPKEY ERR ' .. tostring(err))); return
    end
    if line == 'SWAPKEY?' then reply('SWAPKEY ' .. (registry.key() and 'set len=32' or 'missing')) end
end
uart.on(UART_ID, 'receive', function(id, len)
    buf = buf .. (uart.read(id, len) or '')
    while true do
        local i = buf:find('\n', 1, true); if not i then break end
        local line = buf:sub(1, i - 1):gsub('\r$', ''); buf = buf:sub(i + 1)
        handle(line)
    end
    if #buf > 256 then buf = '' end
end)
```

  串口发送 `SWAPKEY <keyHex>`，回 `SWAPKEY OK`；再发 `SWAPKEY?`，回 `SWAPKEY set len=32`。之后换电指令应回 `ack 0`。
- 平台已改为全网密钥：旧的逐柜密钥（含 208820882721 现有的 k1）在平台发布后失效，柜机须按上面写入新的网络密钥后才能换电。
- 风险（用户已接受）：任一柜机被读出密钥，可为所有柜机伪造开门指令。签名原文含柜号、本次连接 challenge 和订单号，仍防跨柜、跨连接重放。
